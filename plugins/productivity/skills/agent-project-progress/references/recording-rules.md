# Recording Rules

Use this reference to decide what belongs in `project/PROGRESS.md` and what does not.

## Record

- Meaningful implementation progress.
- Changed repositories or project areas.
- Important decisions and the reason behind them.
- Incomplete work, with enough context for the next session to pick it up.
- Verification status: what was run, what passed, what was skipped.
- Commands that matter (e.g. migration commands, verification scripts).
- Concrete next steps.
- Blockers, risks, and open questions.

## Do not record

- Every file opened.
- Every minor edit.
- Every command attempt unless it matters.
- Speculative thoughts that do not affect the project.
- Private reasoning or thought-stream commentary.
- Noisy chronological logs.

## Style

- Prefer concise project-level summaries over detailed transcripts.
- Convert relative dates (e.g. "today", "Thursday") to absolute dates so the file stays interpretable later.
- Update existing sections in place rather than appending new ones for every milestone.
- Group work by repository or project area using the actual discovered names.

## When to update

- At the start of a non-trivial task, after reading the existing progress.
- After understanding the workspace and affected areas.
- After meaningful implementation milestones.
- After tests or verification.
- When blockers, risks, decisions, or open questions appear.
- Before the final response for non-trivial tasks.

Do not update progress for every tiny action.
